    MnesOS Implementation Plan – 2026-05-16¶

    This plan outlines the implementation strategy for decoupling the MnesOS frontend and backend for cloud deployment. Tasks are structured as JIRA-style cards to enable clear ownership for the decoupled build process and Makefile enhancements.

    [MnesOS-260516-01] Build – Web-Client Static Generation¶

    • Status: Backlog
    • Objective: Enable pure static builds of the web-client for CDN deployment.
    • Description:
      • Ensure npm run build in web-client/ creates a dist/ directory entirely independent of the Python backend.
      • Implement environment variable injection (e.g., VITE_API_BASE_URL) at build time so the static bundle can route API requests to a remote backend.

    [MnesOS-260516-02] Build – Backend Cloud Containerization¶

    • Status: Backlog
    • Objective: Create a lightweight, secure Docker image for the Python API.
    • Description:
      • Create a separate Dockerfile.cloud (or multi-stage target) that explicitly excludes the web-client directory and Node.js dependencies.
      • Ensure the resulting image only contains the FastAPI application and its Python dependencies.

    [MnesOS-260516-03] Engine – Conditional Static File Serving¶

    • Status: Backlog
    • Objective: Allow the backend to run in a pure-API mode without serving the GUI.
    • Description:
      • Introduce an environment variable (e.g., MNESOS_SERVE_FRONTEND) defaulting to True (for local mode).
      • Update main.py to only mount the StaticFiles directory if this variable is true.

    [MnesOS-260516-04] Engine – Production CORS Configuration¶

    • Status: Backlog
    • Objective: Securely allow frontend CDN domains to communicate with the backend API.
    • Description:
      • Implement dynamic CORS origins via environment variables (e.g., ALLOWED_ORIGINS).
      • Configure FastAPI's CORSMiddleware to strictly allow these origins in cloud mode, preventing unauthorized cross-origin requests.

    [MnesOS-260516-05] Tooling – Makefile Cloud Build Targets¶

    • Status: Backlog
    • Objective: Provide operators with simple commands to build decoupled artifacts.
    • Description:
      • Add make build-cloud-frontend to compile the web-client with injected cloud API variables.
      • Add make build-cloud-backend to build the pure-API Docker image.
      • Add a unified make build-cloud command that accepts CLI parameters (e.g., API_URL) to orchestrate these split builds seamlessly.

    [MnesOS-260516-06] Database – Cartridge Asset Routing¶

    • Status: Backlog
    • Objective: Ensure cartridge binary assets remain decoupled from the backend.
    • Description:
      • Enforce that cartridge definitions stored in the backend database use absolute HTTP links for binary assets (images, audio) rather than relative paths.
      • Ensure the web-client fetches these assets directly from their remote storage (e.g., S3 buckets, IPFS) rather than routing requests through the FastAPI backend.

    [MnesOS-260516-07] Engine – Interactive Payload Schema Definition¶

    • Status: Backlog
    • Objective: Establish the API contract for rendering interactive UI elements instead of plain text.
    • Description:
      • Define a Pydantic schema for InteractivePayload, supporting action_form (buttons, checkboxes) and minigame variants.
      • Update the YARE engine state schema to natively track _pending_interaction flags, ensuring the backend knows when it is waiting for a structured response.

    [MnesOS-260516-08] Frontend – Interactive Form Renderer¶

    • Status: Backlog
    • Objective: Enable the web-client to render structured forms and decision buttons.
    • Description:
      • Build React components that parse InteractivePayload for action_form variants.
      • Input Locking: When a form is active, explicitly disable the free-text chat input bar to enforce choice-based navigation.
      • Reload Handling: Ensure that if the page is refreshed, the UI re-initializes the pending form from the _pending_interaction state.
      • UI Lifecycle: Automatically collapse or hide the form UI once a narrative response is received without a payload.

    [MnesOS-260516-09] Frontend – Standardized Minigame Suite¶

    • Status: Backlog
    • Objective: Implement a suite of standard mini-games for mechanical resolution.
    • Description:
      • Develop the "Standardized Mini-game Set" within the React client.
      • Implement the game-state reporting bridge to send completion payloads to the Input Router.
      • Ensure games correctly scale based on the provided difficulty/stat multipliers from the backend.

    [MnesOS-260516-10] Graph – Input Router Node for Pending States¶

    • Status: Backlog
    • Objective: Allow the graph to cleanly handle asynchronous two-part interactions statelessly.
    • Description:
      • Introduce an Input Router node at the start of the LangGraph execution.
      • If _pending_interaction is present in the loaded DB state, bypass the LLM intent-parsing node completely.
      • Conflict Validation: Return a 409 Conflict or error if the input type does not match the pending state (handling multi-tab/stale sessions).
      • Strictness: Reject any free-text input while an interaction is pending, returning a system message to the user.
      • Route valid structured input directly to a deterministic resolution node.

    [MnesOS-260516-11] YARE – Python Authoring Specification (yare.py)¶

    • Status: Backlog
    • Objective: Enable cartridge developers to write the full YARE specification using Python.
    • Description:
      • Define the formal schema mapping for the full YARE specification (Conditions, Actions, State Schemas, Global Lore) into a yare.py SDK.
      • Implement the Python compiler that serializes decorators and function definitions into the standard YARE YAML Intermediate Representation.
      • Maintain the 1-to-1 mapping requirement where a single Python function compiles into a single, deterministic YARE event trigger.

    [MnesOS-260516-12] YARE – JavaScript Authoring Specification (yare.js)¶

    • Status: Backlog
    • Objective: Enable cartridge developers to write the full YARE specification using JavaScript/TypeScript.
    • Description:
      • Define the formal schema mapping for the full YARE specification into a yare.js SDK.
      • Implement the JavaScript compiler that serializes functions and object literals into the standard YARE YAML Intermediate Representation.
      • Establish SDK patterns for programmatic rule generation using JS-native features like loops and helper modules.

    [MnesOS-260516-12] YARE – SDK Support for Asynchronous Interactive Events¶

    • Status: Backlog
    • Objective: Formalize the developer experience for creating multi-turn interactive state machines across both SDKs.
    • Description:
      • Establish the explicit SDK syntax for triggering interactive payloads (e.g., ctx.ui.send_form, ctx.ui.trigger_minigame).
      • Define the pattern for accessing structured return values in subsequent resolution events (e.g., ctx.input.form_value or ctx.input.score).
      • Enforce the convention of explicitly clearing the _pending_interaction flag within the resolution function to unlock the standard conversational game loop.
